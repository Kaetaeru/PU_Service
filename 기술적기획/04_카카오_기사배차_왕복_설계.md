# 04. 카카오 기반 기사 배차 왕복 설계

> 목표: 고객의 공항 픽업/샌딩 요청을 `PU_Service`가 접수하고, 기사에게 카카오톡으로 배차 정보를 전달한 뒤 기사의 배차 응답(예상 도착/픽업 시각, 차량 번호 등)을 받아 고객에게 다시 전달한다.

## 1. 핵심 결론

카카오톡을 단순 메신저처럼 서버가 자유롭게 읽는 구조로 설계하지 않는다.

`PU_Service`가 예약과 배차 상태의 source of truth가 되고, 카카오는 **알림/사용자 액션 전달 채널**로 사용한다.

권장 1차 구조는 다음과 같다.

```text
[고객 Transfer HTML]
        |
        | POST /v1/transfer-requests
        v
[PU_Service]
        |
        | 기사에게 카카오 알림
        v
[기사 KakaoTalk]
        |
        | "배차 수락/정보 입력" 보안 링크
        v
[Driver Response Web]
        |
        | ETA / 차량번호 / 기사정보
        v
[PU_Service]
        |
        | 고객 카카오 알림
        v
[고객 KakaoTalk]
```

대안으로 기사 전용 카카오 채널 챗봇을 만들고 챗봇 스킬 서버를 `PU_Service`에 연결할 수 있다. 이 경우 기사 발화와 챗봇 파라미터가 HTTP POST로 `PU_Service`에 전달된다. 다만 **선제적으로 기사에게 배차 요청을 보내는 수단**과 자유 텍스트 파싱 문제를 별도로 해결해야 하므로, 1차 운영에서는 `카카오 알림 + 서명된 응답 링크`가 더 단순하고 안전하다.

## 2. 전체 업무 흐름

### Step 1 — 고객 요청 접수

고객이 기존 Stay Pachira transfer HTML에서 정보를 입력한다.

현재 입력:

- pickup / drop-off
- 대표 게스트명
- 날짜/시간
- 항공편
- 인원
- 공항/서울역
- 숙소
- 카시트
- 터미널 경유
- 비고

왕복 배차를 위해 추가가 필요한 입력:

- 고객 연락처(필수 권장)
- 고객 메시지 수신 동의/안내
- 필요 시 현재 위치 공유 동의

`PU_Service`는 요청을 저장하고 `request_id`를 생성한다.

### Step 2 — 고객 위치 확보

"현재 손님의 위치"를 정확히 기사에게 보내려면 단순 숙소/공항 코드와 실시간 위치를 구분한다.

#### 예약 시점 위치

예약 단계에서는 다음과 같이 구조화된 목적지를 가진다.

- `port_code`: ICN / GMP / SEOULSTN
- `stay_code`: PH1 / PH2 / PH3 / SP5 / SP6 / WSR
- 서버 master가 해석한 실제 주소/meeting point

#### 실제 현재 위치

필요 시 고객에게 위치 공유 버튼을 제공한다.

브라우저 Geolocation API 등으로 받은 값은 다음처럼 저장한다.

```json
{
  "latitude": 37.4602,
  "longitude": 126.4407,
  "accuracy_m": 35,
  "captured_at": "2026-08-20T01:20:00+09:00"
}
```

중요:

- 위치는 고객이 명시적으로 허용한 경우만 수집한다.
- 좌표만 보내지 말고 수집 시각과 정확도를 함께 기록한다.
- 공항 실내 GPS는 부정확할 수 있으므로 터미널/게이트/meeting point와 함께 전달한다.
- 배차 완료 후 불필요한 위치 데이터는 보존하지 않는 정책을 둔다.

## 3. 기사에게 보내는 배차 요청

`PU_Service`가 기사 후보 또는 지정 기사에게 카카오 메시지를 발송한다.

메시지에는 운영에 필요한 최소 정보만 넣는다.

예시:

```text
[Stay Pachira 배차 요청]
배차번호: DP-20260820-0142
일시: 8/20 15:40
구분: 공항 픽업
손님: Julia H. / 2명
항공편: KE938
픽업: 인천공항 T1
목적지: Pachira House 1F
카시트: 1개
특이사항: 캐리어 6개
현재 위치: 지도 열기

[배차 수락 및 차량정보 입력]
```

개인정보 최소화 원칙:

- 기사에게 고객 이름 전체가 꼭 필요하지 않으면 일부 마스킹
- 고객 전화번호는 운영상 직접 연락이 필요한 경우에만 제공
- 위치 URL은 만료 가능한 tokenized URL 사용
- 내부 request ID와 기사용 dispatch ID를 구분

## 4. 기사 응답 방식 — 권장 MVP

기사에게 자유 텍스트 답장을 요구하지 않는다.

카카오 메시지의 버튼을 누르면 다음 보안 페이지가 열린다.

```text
/driver/dispatch/{dispatch_id}?token=<signed-single-use-token>
```

기사 입력 항목:

- 배차 수락 / 거절
- 배차 가능 시각 또는 예상 도착 시각(ETA)
- 차량 번호
- 기사명
- 기사 연락처(필요 시)
- 차량 종류/색상(선택)
- 기사 메모(선택)

응답 예:

```json
{
  "decision": "accepted",
  "eta": "2026-08-20T15:30:00+09:00",
  "vehicle": {
    "plate_number": "12가3456",
    "model": "Carnival",
    "color": "Black"
  },
  "driver": {
    "name": "김기사",
    "phone": "010-...."
  }
}
```

서버는 token을 검증하고 배차 상태를 갱신한다.

### 왜 자유 텍스트 카카오 답장보다 이 방식이 좋은가

- 일반 채널 1:1 대화를 `PU_Service`가 임의로 읽는 API에 의존하지 않는다.
- 차량번호와 ETA를 구조화된 데이터로 받는다.
- 오타/파싱 오류를 줄인다.
- 어떤 기사에게 보낸 요청인지 `dispatch_id`로 확실히 연결한다.
- 중복 수락과 만료된 배차 요청을 서버에서 거절할 수 있다.

## 5. 기사 응답 방식 — 챗봇 대안

기사 전용 카카오톡 채널 + 챗봇 관리자센터를 사용할 수도 있다.

```text
기사 발화/버튼
   -> Kakao Chatbot
   -> Skill HTTP POST
   -> PU_Service
   -> Skill response
   -> 기사 KakaoTalk
```

예:

```text
기사: "배차 수락"
봇: "차량 번호를 입력해 주세요"
기사: "12가3456"
봇: "예상 도착 시각을 입력해 주세요"
기사: "15:30"
봇: "배차 정보가 등록되었습니다"
```

장점:

- 기사 입장에서 카카오톡 안에서 완료 가능
- 별도 web UI 사용이 줄어듦

단점:

- 챗봇 블록/파라미터/컨텍스트 설계 필요
- 기사 식별 및 활성 dispatch 연결 규칙 필요
- 선제 배차 메시지 발송 수단은 별도 준비 필요
- free text보다 버튼/파라미터 중심으로 제한해야 안정적

따라서 MVP는 보안 링크 방식, 이후 기사 UX 개선이 필요하면 챗봇 방식으로 확장하는 것을 권장한다.

## 6. 고객에게 배차 결과 반환

기사 응답이 저장되면 `PU_Service`는 즉시 고객 notification job을 만든다.

고객에게 전달할 최소 정보:

- 예약번호
- 확정 픽업/배차 시각 또는 ETA
- 차량 번호
- 차량 모델/색상(있는 경우)
- 기사명
- 기사 연락처(정책상 허용 시)
- meeting point / 현재 위치 안내
- 예약 상태 링크

예시:

```text
[Stay Pachira 픽업 배차 완료]
예약번호: TR-20260820-0091
기사님: 김기사
차량: 검정 Carnival / 12가3456
예상 도착: 15:30
미팅 위치: 인천공항 T1 1층 7번 출구

현재 위치/배차 상태 확인
```

고객 통지는 카카오 알림톡/허용된 채널 메시지 등 실제 계약 가능한 방식으로 adapter화한다.

카카오 발송 실패에 대비해 SMS 또는 웹 상태 페이지 fallback을 고려한다.

## 7. 상태 머신

초안:

```text
requested
  -> dispatch_preparing
  -> driver_notified
  -> awaiting_driver_response
       -> driver_rejected
       -> driver_accepted
            -> assigned
            -> guest_notifying
            -> guest_notified
            -> en_route
            -> arrived
            -> completed

공통 예외:
  -> cancelled
  -> failed
  -> dispatch_expired
```

핵심 원칙:

- `driver_notified`는 메시지 전송 성공일 뿐 배차 완료가 아니다.
- `assigned`는 기사 응답의 ETA/차량번호가 서버에 저장된 후에만 가능하다.
- `guest_notified`는 고객 통지 성공 여부를 별도 추적한다.
- 메시지 전송 상태와 실제 배차 상태를 같은 enum으로 뭉치지 않는다.

## 9. API 경계 초안

### 고객 요청

```http
POST /v1/transfer-requests
```

### 고객 위치 갱신

```http
POST /v1/transfer-requests/{request_id}/guest-location
```

인증되지 않은 임의 사용자가 위치를 덮어쓰지 못하도록 request-scoped secure token이 필요하다.

### 기사 배차 생성

```http
POST /internal/transfer-requests/{request_id}/dispatches
```

### 기사 응답

```http
POST /driver/dispatches/{dispatch_id}/respond
Authorization: dispatch response token
```

### 고객 상태 조회

```http
GET /v1/transfer-requests/{request_id}
```

공개 identifier만으로 개인정보가 노출되지 않도록 status token 또는 인증을 사용한다.

## 10. 카카오 연동 역할

카카오 adapter는 다음 인터페이스로 추상화한다.

```text
sendDriverDispatch(dispatch)
sendGuestAssignment(request, assignment)
sendGuestStatusUpdate(request, status)
```

`PU_Service` 도메인 로직은 특정 카카오 API/공식 딜러사 SDK에 직접 의존하지 않는다.

### 카카오 채널 Webhook 주의

카카오톡 채널의 일반 Webhook은 채널 추가/차단 같은 관계 이벤트용이다. 이를 기사 자유 대화 수신 webhook으로 간주하지 않는다.

### 카카오 챗봇 Skill

기사 채널 챗봇을 쓸 경우 챗봇 시스템이 사용자 발화/파라미터를 Skill server endpoint에 HTTP POST로 전달할 수 있으므로 `PU_Service`가 구조화된 기사 응답을 받을 수 있다.

### 알림톡/비즈메시지

고객/기사에게 정보성 알림을 보내는 방식으로 적합하다. 실제 발송은 카카오 정책과 공식 딜러/파트너 계약, 템플릿 승인 여부를 확인한 뒤 provider adapter를 확정한다.

## 11. 현재 HTML에서 바로 수정해야 할 데이터 요구사항

현재 폼만으로는 왕복 배차에 부족하다.

필수 추가 후보:

1. `guest.phone` — 고객에게 배차 결과를 다시 보내기 위한 수신 좌표
2. 개인정보/메시지 안내 및 필요한 동의
3. 실시간 위치가 필요하면 위치 공유 UX
4. 공항 terminal / meeting point 정보
5. 고객이 재확인할 수 있는 `request_id`/status URL

전화번호 없이 고객에게 비동기 배차 결과를 카카오로 확실히 돌려주는 것은 어렵다. Kakao Login 기반 user identity를 쓰는 대안도 있지만 MVP에서는 전화번호 + 정보성 알림 경로가 단순하다.

## 12. 보안/개인정보

- 기사 메시지에 필요한 최소 고객 정보만 포함
- 위치 링크는 만료시각이 있는 signed token
- 기사 응답 token은 1회성 또는 짧은 TTL
- 차량번호/기사 연락처는 해당 request의 고객에게만 노출
- guest location은 완료/취소 후 짧은 보존 정책 적용
- 로그에 전화번호/정밀 위치/메모 원문을 그대로 남기지 않기
- dispatch와 notification 전 과정을 audit event로 기록

## 13. 실패/재배차

기사 A가 거절하거나 응답 timeout인 경우:

```text
dispatch A -> rejected/expired
PU_Service -> dispatch B 생성
기사 B -> 수락 + ETA/차량번호
PU_Service -> assignment 확정
PU_Service -> 고객 알림
```

기사 여러 명에게 동시에 보내는 fan-out 방식은 중복 수락 경쟁 조건이 생기므로 MVP에서는 **한 번에 한 기사 또는 명시적인 first-accept transaction**만 허용한다.

## 14. 구현 우선순위

### Phase 1 — 고객 접수

- HTML -> `POST /v1/transfer-requests`
- phone 필드 추가
- request persistence/idempotency

### Phase 2 — 기사 배차 왕복

- DriverDispatch 모델
- 기사 notification adapter
- signed response link
- 기사 수락/거절 + ETA + 차량번호 입력
- assignment transaction

### Phase 3 — 고객 리턴

- 고객 notification adapter
- 배차 완료 메시지
- 상태 조회 링크

### Phase 4 — 현재 위치

- guest location capture
- expiry/privacy
- 기사 지도 링크

### Phase 5 — Kakao Chatbot 개선

- 기사 전용 채널/챗봇
- Skill endpoint
- 버튼/파라미터 기반 기사 응답

## 15. 다음 기술 결정

구현 전에 아래만 확정하면 된다.

1. 기사 목록을 누가 관리하는가 — 내부 고정 기사 / 외부 업체 / 복수 업체
2. 기사에게 배차 요청을 어떤 발송 수단으로 보낼 것인가 — 알림톡/채널 메시지/SMS fallback
3. 고객에게 카카오 메시지를 보내기 위해 전화번호를 필수로 받을 것인가
4. 실시간 위치는 예약 즉시 받을지, 픽업 직전 별도 링크로 받을지
5. 배차 응답 timeout과 재배차 규칙
6. 기사에게 공개할 고객 개인정보 범위

이 여섯 결정이 나면 `PU_Service`의 실제 구현 task를 안정적으로 분리할 수 있다.
